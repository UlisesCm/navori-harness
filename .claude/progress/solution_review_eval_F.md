## Findings

- **[BLOCKER]** The chosen plugin-merge precedence ("first-listed wins per key... mirrors the existing spread idiom['s] 'later entry can override a specific key' behavior") is self-contradictory as written and likely to ship the *opposite* of the stated rule. The real idiom at `packages/cli/src/commands/init.ts:268` (`{...ALWAYS_ON_PLUGINS, ...extraPlugins, ...wsPlugins}`) means **later-spread wins**. To make "first-listed workspace wins" per plugin key via that same mechanic, an implementer must spread the N workspaces' plugin dicts in **reverse** list order (`{...wsN.plugins, ..., ...ws1.plugins}`) — the artifact never says this. The natural reading of "mirrors the spread idiom" instead invites `{...ws1.plugins, ...ws2.plugins}` (forward, list order), which gives **last**-listed wins — inconsistent with the scalar rule (`ws1.branchBase ?? ws2.branchBase ?? …`, which naturally gives first-wins with no inversion needed). This is exactly the "genuine design decision" the artifact itself flags as the crux of the ticket (§ Chosen solution 3), and its own Testing Strategy doesn't catch a wrong-order implementation: `workspace-defaults.test.ts`'s proposed case only checks a scalar (`branchBase`) conflict and that engines/plugins from *both* workspaces are *present* (a union check) — never a same-plugin-id, opposite-`enabled` conflict between two workspaces, which is the one case that would actually reveal a reversed-precedence bug. Evidence: `packages/cli/src/commands/init.ts:254,264-268`; artifact §"Chosen solution" item 3 and §"Testing strategy" item 2.

- **[BLOCKER]** `commands/workspace.ts`'s `link` auto-write/mismatch-warn logic (lines 401-408) is not actually redesigned by the artifact, even though its own consumer table lists all three of its behaviors as needing to become list-aware. Under `workspace: string | string[]`: `!config.workspace` (line 401) is always `false` for any populated array (arrays are truthy in JS regardless of length, and the schema enforces `.min(1)`), and `config.workspace !== name` (line 407) always evaluates `true` when `config.workspace` is an array (array vs. string is never `===`), **even when `name` is already a member of that array**. If implemented literally per "Chosen solution" step 5 (which only addresses the "no explicit name → loop" branch), `workspace link <name>` on any multi-workspace repo would print a spurious "config mismatch" warning on every single invocation, including ones where the name given is already correctly registered. Evidence: `packages/cli/src/commands/workspace.ts:376,401,407-408`.

- **[CONCERN]** The design never mentions the checked-in, auto-derived JSON Schema `apps/website/public/schema/navori.config.v1.json` (generated from `NavoriConfigSchema` via `z.toJSONSchema()` in `packages/cli/scripts/gen-schemas.mjs`) or its drift-guard test `packages/cli/src/lib/__tests__/schema-publish.test.ts`, which does a **byte-exact** `expect(onDisk).toBe(serializeSchema(spec))` comparison. The on-disk file currently declares `"workspace": { "type": "string", "pattern": "^[a-z0-9][a-z0-9-]*$" }` — changing `lib/schema.ts`'s `workspace` field to a union **will fail this test** in CI until `pnpm gen:schemas` is re-run. This is precisely the "JSON-schema `$schema` consumers" scenario the review brief asked about, and it's absent from the artifact's "Testing strategy" and "Migration & compatibility" sections. Mechanical to fix once discovered, but a real, concrete, easily-missed step. Evidence: `apps/website/public/schema/navori.config.v1.json:19-22`, `packages/cli/scripts/gen-schemas.mjs:9-13`, `packages/cli/src/lib/__tests__/schema-publish.test.ts:15-30`.

- **[CONCERN]** The `doctor --json` output contract change is understated. "Boundaries & contracts" calls the `scanWorkspaceLink`/`scanWorkspaceDrift` return-type change (single value/null → array) "the one truly breaking internal-API change" and scopes it to "doctor.ts + workspace-drift.ts + their tests" — but both fields are spread verbatim into the `report` object that's JSON-serialized for `navori doctor --json` (`commands/doctor.ts:125,150,194,208`), and the surrounding code explicitly treats that as a CI-facing contract ("JSON consumers (CI pipelines) need the same exit-code semantics..."). No existing test exercises `doctor --json`'s `workspaceLink`/`workspaceDrift` shape (`workspace-link-doctor.test.ts` calls `scanWorkspaceLink` directly as a unit, not through the CLI's JSON output; `find ... doctor*.test.ts` at the command level returns nothing), so a CI script doing `report.workspaceLink.kind` would silently read `undefined` off an array instead of throwing — the exact "breaks silently rather than throw" failure mode the review brief asked to look for. Evidence: `packages/cli/src/commands/doctor.ts:125,150,194,208,212-213`.

- **[CONCERN]** The interactive `init` wizard's free-text `workspace` prompt (`commands/init.ts:450-458`) is left unaddressed beyond "NOT in scope: multiselect upgrade... fast-follow." But that framing undersells the gap: the design's own item 4 teaches users the `configure workspace "a,b"` comma-separated convention, and nothing in the wizard prevents (or helps) a user typing the same convention into this prompt. The prompt has no `validate()` (unlike the `name` prompt at line 428), so a comma-containing value flows straight through (`if (trimmed) workspace = trimmed;`) into `writeConfig` as a single string (line 705), where it hits the KEBAB_STRING regex and fails with an opaque "workspace must be kebab-case" error. The "actual need is covered by --yes/--recommended/--full + configure" justification doesn't hold for this specific path, since interactive `init` (no flags) is neither of those. Evidence: `packages/cli/src/commands/init.ts:450-458,705`.

- **[NOTE]** Consumer-table mislabeling: `commands/init.ts` is listed as a "direct consumer of the singular `config.workspace` field," but every read in the cited range is of `args.workspace` (a citty CLI flag of the same name), not the persisted config field. The distinction matters for scoping the actual diff (a citty `args` parsing/shape change, not a `readConfig`-then-branch change). Evidence: `packages/cli/src/commands/init.ts:110-113,198,200,208-209,235,317,389,705`.

- **[NOTE]** The direct quote of the plugin-merge spread in "Chosen solution" §3 doesn't match the real identifier (`wsDefaults` quoted, `wsPlugins` in the actual code). See Citation accuracy above.

- **[NOTE]** Approach C's rejection holds up, and the review brief's suggested rescue (`navori workspace link --from-config`) doesn't actually save it: `workspace link`'s only existing source of "which workspace(s) should this repo register into" *is* `config.workspace` (`commands/workspace.ts:376`). A `--from-config` reconciliation flag would just read that same field — for it to name more than one workspace, the field would already need to be a list, which is the exact schema change Approach C claims to avoid. So Approach C, taken literally ("don't touch the schema"), can only ever reconcile one membership; a second membership would have to live in some other checked-in artifact, which is a worse version of the same idea, not an alternative to it.
