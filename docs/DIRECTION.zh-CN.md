# 项目方向 — Navori 的权威说明

> **在 Navori 中提出或构建任何东西之前请先阅读本文**（人类或人工智能代理）。
> 本文阐明项目的定位、发展方向，以及应做和不应做的事。
> 任何与本文不变量冲突的想法，都必须先按“变更前需要讨论的事项”处理，之后才能实施。
> 正式决策记录在 `specs/` 中；本文只作摘要并提供链接，不重复决策原文。

## navori 是什么

navori 是一个 npm 包，其命令行工具名为 `navori`。它可以在任意代码仓库中以可重复的方式搭建**多智能体工作框架与 SDD**，并支持多个引擎：Claude Code、原生 Codex（已由规范 0004 实施）、Pi（可选启用；已验证的控制措施见 [`docs/pi.md`](./pi.zh-CN.md)）、通用 `AGENTS.md`、Cursor 和 Copilot。各引擎适配器共用渲染管线，但不承诺功能集完全相同。navori 从唯一事实来源 `navori.config.json` **幂等地**重建各引擎资源，同时保留用户手工编写的内容。目前它是内部投入使用的 MVP，已部署到 15 个 Bonum 仓库；项目采用 Bun workspace monorepo，包含 `@navori/cli`、`@navori/core` 和 `apps/website`。

## 核心愿景

**每个代码仓库在开始 AI 会话时，都应已具备护栏、编排规范、记忆和质量保障；这些内容应可重复生成、可纳入版本控制，且不损害用户已有的工作。** navori 负责生成工作框架，不负责运行智能体工具。它通过技能、权限和协议说明应使用哪些工具、遵循哪些规范，并将这些内容生成成受管理的资源。

navori **首先服务自己的团队**：每项功能都应回答“它能否帮助 Ulises 和 Bonum 更好地工作？”，而不是“它能否让产品更受欢迎？”MVP 已覆盖实际工作流程；下一步应**加固现有功能**，而不是扩大产品范围。

## 工作框架状态

执行期间产生的临时状态保存在当前检出目录中，且与引擎无关：交接记录位于 `.navori/state/handoffs/`，钩子标记位于 `.navori/state/hooks/`。这些文件不纳入版本控制。`progress/current.md`、`progress/history.md` 和 `.navori/presets/` 则属于可版本控制的项目知识。这种区分不会产生隐藏的持久配置：`navori.config.json` 仍是工作框架的唯一事实来源。

## 目标

- **可重复性**：`render` 根据 `navori.config.json` 重建整个工作框架。没有隐藏状态；签入版本控制的配置是唯一事实来源。
- **混合式无损模型**：同步受管理内容，同时完整保留用户编写的内容。核心优势是在不破坏手工成果的前提下重新生成工作框架。
- **多引擎共用一条管线**：新增一个提供方大致只需添加一张声明式映射表，无须重新实现渲染（共享主干，规范 0007/0008）。
- **经得起长期使用的质量**：CLI 和生成资源的行为可预测，并由严格的质量门把关。
- **提高 token 效率**：每次会话都会加载渲染后的工作框架，因此减少常驻内容会持续累积收益（规范 0005/0006）。
- **以工作区为基础**：在不取代仓库专属配置的前提下，补充工作区共享的持久知识（Domain，规范 0011）。

## 非目标

除非出现充分的新理由，否则以下事项明确**不在范围内**：

- **推广产品、品牌建设、营销、商业化、产品本身的国际化，或用 Rust 编写控制平面。**公开文档和网站的国际化是已批准的例外；CLI 本地化仍不在范围内。navori 是供团队自用的工具，不是面向市场的产品（规范 0003）。
- **正式的公共插件生态。**插件是内部软件包，不是市场上的商品。
- **仿照其他工具的选择性安装架构。**
- **在现有功能仍需加固时开发大型新功能。**优先级依次为：质量 > token 效率 > 速度。
- **LSP / Serena（搜索阶梯第 3 级）。**因固定开销过高而放弃（每次会话约 3k token，另需语言服务器）；搜索阶梯止于第 2 级 ast-grep（规范 0005）。CodeGraph（规范 0009）作为低成本本地 AST 索引引入，并非 LSP。2026-09-15，CodeGraph 与 `tgrep`（规范 0017）一同从引擎中移除；这次撤除只是**暂时且不完整的**：当时的计划是从头重做二者并集成，让它们协同工作。

# 838（2026-09-16）结束了这一轮工作。

如今二者又作为可选插件提供，*代码发现*路由会根据问题类型，在结构发现（CodeGraph）与文本发现（tgrep/原生工具）之间选择，而不是靠散文规则决定。重做前的测量结果——CodeGraph 接线正确但调用次数为零；tgrep 按规则执行时为 7.4%，加上机械护栏时为 40.7%——仍作为早期设计记录保存在 [`docs/research/tgrep-como-funcionaba.md`](./research/tgrep-como-funcionaba.md)。这次变化不意味着重新讨论对 LSP/Serena 的否决。
- **让 navori 执行智能体工具。**navori 生成工作框架（技能、允许列表、插件和协议）；grep、ast-grep、测试等工具由智能体运行。
- **“Navori 之声”/应用构建器/4R 审查**——已搁置（规范 0010，后由 0046 取代）。
- **在每台机器的 `~/.claude` 中设置固定的基础规范**（全局层，规范 0010）。该方案未采用：实现成本约 5.5k–6k 行代码，后来随规范 0046 一并退役。因此，在未配置 navori 的仓库中，会话有意不带此工作框架。

## 设计原则与不变量（没有新理由时不重新讨论）

1. **五层级联架构**——Core → Preset → Workspace → Project config（`navori.config.json` + 可选插件）→ Engine adapters。每层都在上一层基础上组合。*原因*：在不重复的前提下，将通用基线与特定技术栈、组织、仓库和引擎的内容分开。
2. **从第一天起支持多引擎**——即使当前只为部分引擎生成资源，核心仍与引擎无关。*原因*：新增提供方不应要求重写管线。
3. **唯一事实来源是签入版本控制的 `navori.config.json`**——`render` 从该配置重建。*原因*：完全可重复，不依赖隐藏状态。
4. **用标记实现混合式同步**——`<!-- navori:managed ... -->` 标记内的内容由工具同步；标记外的内容归用户所有，保持原样。`hash` 用于检测内容漂移；`version` 记录最近一次实际修改区块内容的 navori 版本，而不是负责渲染的版本。因此，新版 CLI 重新渲染未变内容时不会改写文件。`navori.config.json` 中的 `harnessVersion` 记录仓库最近一次实际应用变更的版本，并支持防回滚机制（#1262）。*原因*：幂等地重建内容，不覆盖手工修改，也不制造无意义的 diff。
5. **默认先预览渲染结果**——`render` 不写入磁盘；`--apply` 会先创建备份，再以原子方式写入（fsync）。*原因*：避免磁盘被意外修改。
6. **插件以软件包形式组织**——每个插件可包含设置片段、claude-md 区块、技能、钩子和 doctor 检查等可选内容，并在 Project config 层声明。*原因*：可选扩展保持内聚，无须增加独立层级。
7. **共用一条渲染管线（共享主干）**——清点资源、决定放置位置、备份、写入和修剪都由同一处处理；各引擎通过声明式映射接入该管线（规范 0007/0008）。*原因*：管线修复可同时惠及所有引擎，避免引擎间悄然分歧。
8. **未选择启用时不留下痕迹**——Domain 是**增量式**的：仓库已有自己的 navori 配置时，Domain 会让位，绝不削弱该仓库现有配置。*原因*：工作区级基础设施不能破坏已有仓库。
9. **navori 负责生成，不负责执行**——工作框架告知智能体应使用哪些工具。项目可以选择启用范围严格受限的原生 Codex 集成：它可读取宿主配置和评估结果，并在经过身份验证的人类决策及不可变范围约束下，授权发布一项固定的 PR。引擎仍按原有方式执行。此例外不允许通用执行 API、runner、模型 broker、新依赖、常驻运行界面、全局修改权限/配置/信任，也不豁免 R6/A9/A10。已批准的范围允许实现由宿主授权的浏览器驱动程序；这并不表示控制器、发布效果或配置读取已经实现或获批。若宿主已有受支持的所有权机制且满足保证，应优先使用。任何新的 parent client 都必须执行相同的不可变范围和人类入口限制（[规则](../specs/0050-codex-resultados-equivalentes/design.md)）。*原因*：保持 CLI 简单、工作框架可移植。
10. **自托管**——本仓库及所有非 Bonum 仓库都会提交工作框架（`.claude/`、`CLAUDE.md` 和 `navori.config.json`）：Navori 自己也使用自己的工具。按照惯例，`/bonum` 下的仓库会忽略本地工作框架。

## PR 与验证的单位

功能交付是 PR 的单位；里程碑是验证和提交的单位。小型规范用一个 PR 完成；大型规范按 `sdd.deliveries` 拆为 2 至 4 个 PR。每个 PR 都必须针对最终将发布的确切内容运行完整质量门。项目不设集成分支：各交付按顺序合并到 `prTarget`。Master plan 也遵循同一规则。详情与依据见 [`docs/research/distribucion-entregas-agentes.md`](./research/distribucion-entregas-agentes.md)。

## 按接入表面划分的准入标准

添加新表面（插件、MCP 服务器、托管区块或技能）时，机制的准入顺序是：常驻规则 → 按需技能 → MCP → 本地 CLI → 直接 API。应优先采用运行时表面最小、token 开销最低、活动部件最少的方案。这与 [`docs/EXTENDING.md`](./EXTENDING.zh-CN.md) 所讨论的维度不同：该文按知识归属排列仓库知识的存放位置，即用户区段 → 项目本地技能 → 本地预设 → 插件 → 核心。在归属维度上，常驻的核心区块成本最高，应作为最后选择。这两个维度互不替代：一个决定采用什么机制，另一个决定知识应放在哪里。

优先考虑 Claude，优先使用宿主原生能力：只有宿主不再提供所需能力时，才考虑驱动程序。是否需要驱动程序应由类型化清单决定，而不是依靠散文规则。生成的对照表见 [`native-overlap.md`](./native-overlap.md)。

只有同时满足以下**两个条件**，MCP 服务器才值得接入：(1)**普遍适用**——几乎所有会话都会用到，而非仅服务于小众场景；(2)**MCP 优于由技能封装的 CLI 或 API**——任务确实需要 MCP 独有的能力，例如交互式会话状态、流式传输、身份验证握手或结构化浏览。无状态的请求/响应任务应由技能处理，无须增加服务器。

其他工作框架（ECC）为该规则提出的成本理由是：每个默认连接器都会在每次会话中加载约 30 个工具 schema。但这一成本说法对 Claude Code 已经过时：[官方上下文窗口文档](https://code.claude.com/docs/en/context-window)确认，MCP 工具 schema **默认延迟加载**，只有通过工具搜索按需调用时才加载；始终加载的只有工具名称列表。本文采用的是**架构层面的标准**（无状态任务交给技能，减少活动部件），而不是 ECC 的 token 成本论据。

目前，`packages/core/core-assets/` 没有声明任何 `mcpServers`，默认连接器数量为零。这条规则用于评估未来的提案，不是对现状的审计。

**已撤下的表面**（记录表面、结论和替代方案，避免他人不了解测量依据便重复提案）：目前没有。`tgrep` 与 `codegraph` 曾在 2026-09-15 至 #838（2026-09-16）期间按此标准评估。此前的测量结果，以及它为何不属于“已判定价值过低”，见 [`docs/research/tgrep-como-funcionaba.md`](./research/tgrep-como-funcionaba.md)。

## 智能体准入标准

只有在至少能保证以下三项之一时，才应引入来自 core 或 preset 的智能体。如果一项也无法保证，该智能体就是**可裁撤的**，应提议退役（[规范 0031](../specs/0031-admision-de-agentes/requirements.md)）。

- **质量：** 结果经过验证后优于主线程可能产出的结果。例如，在全新上下文中独立复核；使用编排器无法自行指定的模型层级；或使用主线程不应加载的专业上下文。
- **速度：** 将彼此独立的工作并行分派，从而缩短总耗时。
- **Token：** 扣除冷启动成本后仍有**净节省**（规范 0027 按 `cache_creation` 价格测得约 25k token）。例如，把主上下文不会阅读的大量输出留在子代理中，或将机械性工作交给成本更低的模型层级。

申请规则：

- **优先级顺序适用于各个维度：**低优先级收益不能以牺牲高优先级目标为代价（质量 > token 效率 > 速度）。例如，并行实现带来的提速不能抵消质量下降。
- **每项提案都必须说明**它提供的保证、衡量该保证的信号、相对于产出的启动成本，以及带日期的退役标准（例如，连续 N 天没有调用 → `RETIRED_AGENTS`）。
- **新智能体默认关闭**，除非有测量信号证明应启用。例外是 `architect`（规范 0032 R35）：用户决定始终启用它，不设开关，因为是否触发由 `navori plan classify` 决定的级别（2/3）控制，而非模型判断，因此成本有界，无须另设开关。
- **扩展现有智能体的职责**也必须在部署前通过同样的检验；每次委派的冷启动成本都计入 token 维度。

本仓库的本地技能 `author-agent` 在提出或评审智能体时应用这套标准。

## 如何在约束范围内贡献（人类与智能体）

1. **先阅读本文档**，再阅读 `docs/architecture.md`（了解渲染和各层的工作方式），以及你准备修改领域对应的规范（`specs/000X-*.md`）。

   开始编写前，阅读 [`docs/EXTENDING.md`](./EXTENDING.zh-CN.md)，**确定改动最适合放在哪一层**。该文列出五个去处，按成本由低到高排列；通常最小的改动效果最好。若已有技能覆盖该主题，在技能中补充规则能更早传达给智能体，也能沿用现有权威来源。指南还列出四个问题，帮助完善提案。
2. **正式决策应记录在 `specs/` 中。**不要通过 PR 引入新的方向。需要架构决策时，先将其写入规范。遵守规范标题声明的状态（`proposed`、`planning only — NO implementar` 或 `EJECUTADA`），并**对照代码核实**，因为代码反映的状态更新（参见“参考资料”）。
3. **质量门（修改 `packages/cli` 后关闭工作前必须执行）**——在 monorepo 根目录运行 `pnpm check`。CI 的 `quality` 作业也运行此命令；未通过时 PR 会失败。

   质量门只在**一个地方**定义：`navori.config.json` 的 `qualityGate.full`。`pnpm check` 是它的别名，`CLAUDE.md` 的受管理区块也由此生成。本文刻意不重复列出命令，避免出现不同步的副本；#508 就曾发生过这种情况。

   命令未体现的细节——何时需要重新生成镜像、如何处理 golden snapshot，以及哪些改动属于纯文档改动——请参阅 `CONTRIBUTING.md`。
4. **提交**：使用 Conventional Commits，以墨西哥西班牙语编写，并保持每次提交原子化。
5. **分支与 PR**：每个工单都从 `dev` 创建新分支，并向 `dev` 提交 PR。只有从 `dev` 发布的版本 PR 才会进入 `main`，并采用 merge commit（配置见 `navori.config.json` 的 `branchBase` / `prTarget`）。不要提交 `/bonum` 仓库的本地工作框架。
6. **记忆（engram）**：如果消息提到 navori，开始时运行 `mem_search`；设计决策确定后主动运行 `mem_save`；结束前运行 `mem_session_summary`。

## 约定：带类型化绑定的自足规则（问题 #816）

该约定要求规则在本行说明义务，并将原因链接到唯一责任来源，而不是内联重复；它借鉴了 dsh 模式
（[来源](research/deepseek-harness-lessons.md#32--el-patrón-canónico)）：

```
- **<obligación>**: <condición o excepción, si hace falta> (`[<ancla>](<ruta>)`).
```
锚点词汇仅限以下四种，每种都指向 navori 已有的一类责任来源（不另造新类别）：

| 锚点 | 对应责任来源 |
|---|---|
| `[rule]` | `specs/` 中规定行为的正式规范 |
| `[why]` | `docs/DIRECTION.md`、`docs/architecture.md` 或 `docs/research/` 中完整说明权衡的不变量或章节 |
| `[decision]` | 尚无规范或文档时，记录决策的 GitHub issue 或 PR |
| `[scope]` | `CLAUDE.md` 中说明规则适用与不适用范围的技能或章节 |

模式规则：

- **每条规则只设一个责任来源。**如果原因已在 `docs/DIRECTION.md` 或某份规范中说明，规则就不再复述，只需链接。重复记录会产生本约定旨在消除的内容漂移。
- **跨文件链接不使用标题片段。**目前没有质量门校验 `#slug` 锚点（见 [`deepseek-harness-lessons.md`§3.3](research/deepseek-harness-lessons.md#33--qué-significa-para-navori) 中的发现）；文件级链接通过 `test -f` 检查，不会因目标标题改名而失效。同一文件内的片段（例如本节中的链接）则不同：Markdown 可以直接解析，无须依赖其他渲染器的 slug 生成规则。
- **要将该约定推广到受管理区块，必须先实现 `verify-md-links`**——上述 `§3.3` 已将其列为前提。在质量门具备之前，只在具体、低风险的位置使用该约定，不要大范围推广。
